# macOS 开源软件如何检测「媒体播放」— 技术调研

> 调研目标：梳理 macOS 平台开源应用检测「当前是否有媒体在播放 / 正在播放什么」的主流技术方案、代表项目、关键 API，以及 macOS 15.4 之后私有框架失效的应对方式。
> 适用背景：WallFlux 当前用 `CGEventTap` + 辅助功能(AX) 判断显示器「活跃/闲置」。若想增加「某屏幕正在播放视频/音乐则视为活跃」的能力，本调研给出可复用的检测手段。
> 调研时间：2026-08-08
>
> **实施状态：** WallFlux 已按 §6 建议将「媒体播放保持活跃」的主检测切换到 **方案 B'（CoreAudio 进程级）**（feature/audio-process-ignore 分支）：纯公开 API、零授权、区分具体进程，并基于累积发现记录增设「声音应用」忽略管理（设置页第三 tab）。MediaRemote / perl 中转与 `MediaRemoteMini.dylib` 已移除。方案 A'（JXA 获取歌名等元数据）留作未来可选增强。

## 0. 结论速览（TL;DR）

| 方案 | 能否拿到「正在播放什么」（标题/作者/封面） | 能否拿到「哪个 App 在播」 | 能否拿到「是否真的在出声」 | 是否私有 API | macOS 15.4+ 是否可用 | 备注 |
|------|------|------|------|------|------|------|
| **A. MediaRemote 私有框架（直接调用）** | ✅ | ✅ | ✅（isPlaying / playbackRate） | ✅ 私有 | ❌ **已失效**（需 entitlement） | 经典方案，菜单栏类 App 最爱 |
| **A'. MediaRemote 通过 JXA/osascript 中转** | ✅（不含封面） | ✅ | ✅ | ✅ 私有（但由系统 osascript 代持） | ✅ **可用** | 15.4+ 唯一不破坏系统的解法 |
| **B. CoreAudio HAL（系统级是否出声）** | ❌ | ❌（仅设备级） | ✅ `kAudioDevicePropertyDeviceIsRunningSomewhere` | ❌ 公开 | ✅ | 只回答「有没有声音」，不动 metadata |
| **B'. CoreAudio 进程列表（per-process）** | ❌ | ✅（PID / BundleID） | ✅ `kAudioProcessPropertyIsRunningOutput` | ❌ 公开 | ✅ | sountop 的做法，能列出谁在出声 |
| **C. AppleScript / ScriptingBridge（单 App）** | ✅（仅 Music/Spotify 等支持脚本的） | ✅ | ✅ | ❌ 公开 | ✅ | 需用户授权「自动化」；覆盖面窄 |
| **D. NSWorkspace / 分布式通知** | ❌（无标准通知） | ⚠️ 间接 | ❌ | ❌ 公开 | ✅ | 没有统一的「媒体播放」系统通知 |
| **E. 官方 NowPlaying 框架（WWDC 2026 新公开 API）** | ✅ | ✅ | ✅ | ❌ 公开 | ✅（需 macOS 26+） | 未来正道，但 WallFlux 最低支持 14，暂无 |
| **F. CGEventTap 媒体键** | ❌ | ❌ | ❌ | ❌ 公开 | ✅ | 只能感知「用户按了播放键」，不知真实状态 |

**给 WallFlux 的建议（见 §6）：** 若只想判断「显示器是否该算活跃」，最省事的是 **方案 B（`isRunningSomewhere`）或 B'（per-process）**，纯公开 API、零授权、零风险；若想做得更精致（显示正在播放的歌名），再用 **方案 A'（JXA）** 作为可选增强。

## 1. 方案 A：MediaRemote 私有框架（直接 dlopen）

这是最主流、信息最全的手段。控制中心「正在播放」、Touch Bar、Siri 都用它。原理：运行时加载系统私有框架 `/System/Library/PrivateFrameworks/MediaRemote.framework`，取出 C 函数指针直接调用。

### 关键函数（符号名长期稳定）
- `MRMediaRemoteGetNowPlayingInfo(queue, block)` — 取当前播放信息字典
- `MRMediaRemoteGetNowPlayingApplicationIsPlaying(queue, block)` — 仅取「是否在播放」的布尔
- `MRMediaRemoteRegisterForNowPlayingNotifications(queue)` + 监听通知：
  - `kMRMediaRemoteNowPlayingInfoDidChangeNotification`
  - `kMRMediaRemoteNowPlayingApplicationIsPlayingDidChangeNotification`
- 信息字典字段：`kMRMediaRemoteNowPlayingInfoTitle / Artist / Album / Duration / ElapsedTime / PlaybackRate / ArtworkData / ClientBundleIdentifier …`

### 代表开源项目
- **NowPlayingMenuBar**（TrevorBurnham）：菜单栏显示正在播放。明确标注「macOS 15.4 起所用 API 完全失效，已停止维护」。代码改编自 Aerial（John Coate）。
- **nowplaying-cli**（Stealthii）：CLI 取/控媒体，列出全部字段名映射。Homebrew 可装。
- **NowPlayingReporter**（dagarou）：把播放变更以 JSON 流输出，供外部消费。
- **LyricsX / MxIris-LyricsX-Project mediaremote-adapter**：把 MediaRemote 封装成 Swift 包，自带 Perl 桥接绕沙盒。被 LyricsX、Music Presence 等使用。
- **media-remote**（escfex，Rust 绑定）：完整 Rust binding，文档最全。

### 代码骨架（Swift）
```swift
let bundle = CFBundleCreate(
    kCFAllocatorDefault,
    NSURL(fileURLWithPath: "/System/Library/PrivateFrameworks/MediaRemote.framework")
)!
let ptr = CFBundleGetFunctionPointerForName(bundle, "MRMediaRemoteGetNowPlayingInfo" as CFString)
typealias Fn = @convention(c) (DispatchQueue, @escaping ([String: Any]) -> Void) -> Void
let getInfo = unsafeBitCast(ptr, to: Fn.self)

getInfo(DispatchQueue.main) { info in
    let title = info["kMRMediaRemoteNowPlayingInfoTitle"] as? String
    let rate = info["kMRMediaRemoteNowPlayingInfoPlaybackRate"] as? Double
    let isPlaying = (rate ?? 0) > 0
    print("playing=\(isPlaying) title=\(title ?? "")")
}
```
**限制：** 私有框架 → 不能上 Mac App Store（WallFlux 本来就走 DMG/Homebrew，不上 MAS，这点不冲突）；但 **macOS 15.4 起失效**（见 §3）。

## 2. 方案 B：CoreAudio HAL（只回答「有没有声音」）

如果你关心的只是「这块屏幕该不该算活跃 / 有没有音频在跑」，CoreAudio 是更干净的公开 API，不需要任何私有框架或授权。

### B-1. 设备级「是否在出声」
```swift
var addr = AudioObjectPropertyAddress(
    mSelector: kAudioDevicePropertyDeviceIsRunningSomewhere,
    mScope: kAudioObjectPropertyScopeGlobal,
    mElement: kAudioObjectPropertyElementMaster
)
var isRunning: UInt32 = 0
var size = UInt32(MemoryLayout<UInt32>.size)
AudioObjectGetPropertyData(defaultOutputDevice, &addr, 0, nil, &size, &isRunning)
let audioActive = isRunning != 0
```
> 文档原文：1 = 设备至少在某一进程中被使用，0 = 完全没跑。
> **坑：** 它只证明 IOProc 在跑，不保证真的有非静音信号输出（可能只是静音流）。对「防闲置」足够，对「精确判断」不足。

可注册属性监听（`AudioObjectAddPropertyListener`）实现事件驱动、近零 CPU，不必轮询。

### B-2. 进程级「谁在出声」（更实用）
CoreAudio 提供进程对象列表，可逐个查 PID / BundleID 与「是否正在输出」：
- `kAudioHardwarePropertyProcessObjectList` — 枚举所有音频客户端进程
- `kAudioProcessPropertyPID` / `kAudioProcessPropertyBundleID` — 身份信息
- `kAudioProcessPropertyIsRunningOutput` / `IsRunningInput` — 是否正在出/入声

**代表项目 sountop**（Coalesce-Software-Inc，MIT）：`top` 风的音频进程监视器，正是用上面这组 API 实时列出「哪些进程在出声」。它能区分输出/输入，且不需要私有框架。

**对 WallFlux 的价值：** 可以列出「正在输出音频的 App + 其窗口所在屏幕」，从而把该屏幕判为活跃——比单纯 `isRunningSomewhere` 更精细，且仍然 100% 公开 API。

## 3. macOS 15.4 之后发生了什么（必读）

从 **macOS 15.4** 起，Apple 在 `mediaremoted` 守护进程里加了 **entitlement 校验**：

- 旧方式（任何进程直接 dlopen MediaRemote 调用）→ 守护进程检查调用方代码签名的 entitlement，缺则 **超时 / 返回空**，`MRMediaRemoteGetNowPlayingInfo` 等读取函数全部失效。
- 控制类函数（`MRMediaRemoteSendCommand`）部分情况下还能用，但拿不到状态，整体不可用。

### 两条绕行路线
| 路线 | 机制 | 要关 SIP？ | 能否分发 |
|------|------|-----------|----------|
| **代码注入（patch mediaremoted）** | 用 MediaRemoteWizard 等注入守护进程跳过校验 | ✅ 必须 | ❌ 不适合分发给用户 |
| **JXA / osascript 中转** | 用系统自带、`/usr/bin/osascript`（Apple 签名、带 entitlement）代为执行 JS，再解析 JSON | ❌ 不需要 | ✅ 可用 |

**结论：JXA 是唯一对用户友好、不需关 SIP 的解法。** 代表实现：
- **WhatsPlaying**（r3pr3ss10n）：菜单栏显示正在播放，专门因 15.4 改用 osascript+JS，每 2 秒刷新。
- **mediaremote-adapter（ungive / Alexander5015 分支）**：15.4+ 全功能可用，靠 osascript 桥接；Music Presence、media-control（brew）都在用。
- **media-remote（escfex）** 的 `NowPlayingJAX`：把 JXA 封装成带 `update_interval` 轮询的接口。

### JXA 代码片段（15.4+ 取播放信息，无封面）
```javascript
// 通过 osascript 执行；注意 artwork 拿不到
const req = $.MRNowPlayingRequest.alloc.init;
req.includeMetadata = true;
req.includeArtwork = false;
const info = $.MRMediaRemoteGetNowPlayingInfo(req);
// info 为字典：kMRMediaRemoteNowPlayingInfoTitle / Artist / PlaybackRate ...
```
> 局限：拿不到专辑封面（`ArtworkData` 恒为空）；且是轮询（osascript 调用有开销），做不到真实时推送。

## 4. 方案 C：AppleScript / ScriptingBridge（单 App）

对 Apple Music、Spotify 这类提供脚本接口的 App，可用 AppleScript 直接问：
```applescript
tell application "Music"
    if player state is playing then return {name of current track, artist of current track}
end tell
```
- 优点：公开 API、稳定、能拿到精确字段与播放进度。
- 缺点：每个 App 要单独适配；首次需用户授予「自动化」权限；浏览器里的 YouTube 等网页播放覆盖不到。
- 适合做「精细显示歌名」的可选增强，不适合作为唯一检测源。

## 5. 方案 E（前瞻）：官方 NowPlaying 框架

Apple 在 **WWDC 2026** 推出了公开的 **`NowPlaying`** 框架（`import NowPlaying`，`MediaSessionRepresentable` / `MediaPlaybackSnapshot` 等可观察 API），用于把 App 自身播放投射到锁屏、控制中心、CarPlay。
- 这是未来「读取/响应系统媒体状态」的**官方正道**。
- 可用性：需 **macOS 26+** 部署目标。WallFlux 当前最低支持 macOS 14，短期用不了，但值得在路线图里标记：等最低部署版本升到 26 后，应优先迁移到该公开框架，彻底摆脱私有 API 与 JXA 绕行。

## 6. 对 WallFlux 的具体建议

WallFlux 的「活跃 / 闲置」判定目前依赖输入（键鼠 / AX 聚焦屏幕）。加入媒体检测可解决一个盲区：**用户没动键鼠、但正在看视频/听歌的全屏屏幕，不应被判为闲置去循环壁纸或微跳**。

推荐的分层方案：

1. **主检测（公开、零风险）：CoreAudio 进程级（方案 B'）**
   - 用 `kAudioHardwarePropertyProcessObjectList` + `kAudioProcessPropertyIsRunningOutput` 拿到「正在输出音频的 App 的 PID/BundleID」。
   - 配合 `CGWindowList` 把该 App 的前台窗口定位到 `NSScreen.displayID`（与现有 `frontmostWindowDisplayID()` 逻辑复用）。
   - 该屏幕标记为「媒体活跃」，暂停其闲置计时器。
   - 优点：公开 API、不需辅助功能权限、不需私有框架、macOS 14 即可用、对视频和音乐都有效。

2. **可选增强（若想显示「正在播放：歌名」）：JXA 中转（方案 A'）**
   - 通过 osascript 取 `Title/Artist/isPlaying`，菜单栏/设置里展示。
   - 注意 15.4+ 才需要此路径；14–15.3 可直接 dlopen MediaRemote。
   - 封面拿不到，且是轮询，仅作锦上添花，不要作为「活跃判定」的依赖（否则 15.4 直接调用会失效）。

3. **不要做：** 依赖 `kAudioDevicePropertyDeviceIsRunningSomewhere` 单独判断（只能设备级，区分不了屏幕）；也不要为「活跃判定」而依赖私有 MediaRemote 直接调用（15.4 失效会静默退化）。

4. **路线图：** 待 WallFlux 最低部署版本升到 macOS 26，迁移到官方 `NowPlaying` 框架统一收口。

## 8. 一句话总结

- **只想知道「有没有媒体在播/哪块屏幕在播」** → 用 **CoreAudio 进程级公开 API**（sountop 范式），最稳最干净。
- **想知道「播的是什么」且要兼容 15.4+** → 用 **JXA/osascript 中转 MediaRemote**（WhatsPlaying/mediaremote-adapter 范式）。
- **直接 dlopen MediaRemote** 是旧时代最香的方案，但 **15.4 已死**，新项目别再把它当主检测源。
- **未来** → 等部署版本到 macOS 26，改用官方 **NowPlaying** 框架。
